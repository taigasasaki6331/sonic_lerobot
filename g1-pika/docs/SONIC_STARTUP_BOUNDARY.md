# SONIC実機移行の境界

2026-09-24、固定コミット087f9ac01d46f6d8e4d0b73c01ae64799f292a38の
`gear_sonic_deploy/src/g1/g1_deploy_onnx_ref/src/g1_deploy_onnx_ref.cpp`を読取り調査。
旧Decoupledの起動調査とは別。実機コードの起動・指令送信はしていない。

## 上流コードで確認した事実

- constructor（2250行付近）はMotionSwitcherClientを初期化し、既存modeがあるとReleaseModeを呼ぶ。
  通信・モデルの疎通確認のためだけに通常G1Deployを構築してはいけない。
- INITは既定3秒、実測角からdefault_anglesへ参照を移行し、kp/kdを設定する。
  途中はその時点の実測角を再度使用しており、開始姿勢を固定した単純な軌道とは違う。
- LowCommandWriterは500Hzで最新bufferを送信する。motor mode=1、Dex3送信も同経路。
  PIKAにはそのハンド経路を流用しない。
- CheckSafetyはLowStateの存在と更新年齢500msを確認する。ZMQ切断・GPU停止への対処と同義ではない。
- StopはworkerのWait後、kp=0/kd=8、dq=0/tau=0のdamping目標を作り、一度Writerを呼ぶ。
  その到達や物理的停止を本プロジェクトで確認したわけではない。
- destructor自体にStop呼び出しはない。プロセス強制終了を安全停止として扱わない。

## 現在の実装

記録専用の推論バイナリは上記constructor/Writerを使用しない。
ZMQの入力異常で計算・記録を停止するが、物理停止を実装したとは表示しない。
既存の`hardware_output_enabled=true`は拒否される。変更しても送信機能は起動しない。

2026-10-01：[身体ライフサイクル](BODY_LIFECYCLE.md)の送信なし状態機械を追加。
引継ぎ要求→初期参照→実測q/dqの条件確認→目標受理、入力期限切れ→停止要求→復帰要求を検査する。
保存身体150件では姿勢到達せず、1540件の記録後に入力期限切れで停止要求をラッチした。
診断ACKは人工入力で、実機の引継ぎ/停止/復帰の確認ではない。
続報：[身体SDKアダプター](BODY_IO_ADAPTER.md)の接続コードをbuild-onlyで追加し、
G1/aarch64 object compileのみ確認。実gateway/500Hz送信/物理停止との統合・運用は未完了。
LowCmd native memory/CRCも1540件で照合したが、DDS/CDR通信・実機受理は未検証。
上流INIT/Stopをそのまま実行した検証ではなく、既存オンライン経路への実機出力接続も行っていない。

## 実機送信前に決定・検証する事項

1. 現在の吊り下げ/足接地/作業範囲、現場担当者、確認済みの停止方法。
2. 既存制御からの引継ぎと復帰。モード解除を状態受信の副作用にしない。
3. G1側で成立する停止・通信断処理。GPU/SSHの返答待ちを停止経路にしない。
4. 初期姿勢への移行条件、PIKA装着時の干渉、動的参照の適用条件。
5. 以上に合わせた限定的な実機試験の範囲を提示し、その試験に対して明示許可を得る。

「動かしてよい」という一括許可だけで1〜4が検証済みになるわけではない。
リモコンのソフトウェア統合は追加しない。停止方式をこちらで勝手に選ばない。
