# sonic_lerobot

LeRobot π0 / π0.5 → GEAR-SONIC planner-reference bridge for Unitree G1.
Arms **and waist** are external joint references. Legs are generated by the official planner;
SONIC retains the final whole-body policy. No finger control, no DDS motor publisher, no PIKA.

**Initial core implementation, not commissioned on hardware.** Python protocol and watchdog tests
are runnable without a robot. C++/MuJoCo, PICO tracking, camera synchronization, GPU training and
real-robot validation remain separate acceptance gates; see [validation](docs/validation.md).

## Architecture

```text
GPU PC                         Deployment PC (onboard for real)
π0 / π0.5 inference --RPC----> sonic-gateway --planner PUB :5556--> C++ zmq_manager
state requests       :5560        ^                                  |
                                  +---------g1_debug SUB :5557--------+
                                  |
                            telemetry PUB :5561 --> recorder

PICO source --retargeted planner :5558--> sonic-pico --same RPC--> gateway
```

Only one producer may own the gateway. Start it on the SAME host as deployment: network loss
to the GPU must not stop the local planner heartbeat. Defaults bind loopback; use SSH forwarding
for remote inference (`ssh -L 5560:127.0.0.1:5560 <deployment-host>`). RPC has no authentication;
do not expose it to an untrusted network. Camera traffic is a separate provider interface.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e '.[test]'

```

Learning/recording export additionally needs Linux, the pinned LeRobot dependencies and compatible
PyTorch/CUDA/FFmpeg. `pip install -e '.[learning]'` installs the pinned LeRobot base package;
follow that revision's π0/π0.5 installation instructions for its model-specific dependencies.

## Simulation / real

Install/build the official Gear deployment and model first. In the official repo:

```bash
# sim only, using the official simulation environment
python gear_sonic/scripts/run_sim_loop.py
# separate terminal, in gear_sonic_deploy
./deploy.sh --input-type zmq_manager --zmq-host localhost --zmq-port 5556 sim
# real uses the identical input path; replace sim with real (no simulation loop)
```

On that same host, run `sonic-gateway`. A fresh measured state initializes a held upper-body
reference; the gateway intentionally does NOT start/stop the C++ control policy automatically.
Use the official deployment operator controls to engage the control loop and select planner mode.
G1's physical initial posture must match the chosen startup mode (IDLE). The gateway does not infer
whether a powered-on robot is already kneeling. Real startup from arbitrary poses is unsupported.

## Action / observation contract

`schema.py` is the single source of truth, with a schema hash checked at runtime.

* Action: 17 absolute upper-body angles (radians, official interleaved IsaacLab upper order),
  forward/left velocity (m/s in commanded heading frame), yaw rate (rad/s), planner height (m,
  `-1` means official default), **27 one-hot mode channels**. Total **48**.
* State: 29 measured body angles (MuJoCo/hardware order), normalized IMU quaternion `wxyz`,
  previous applied action. Total **81**. No fake measured base position, speed or height.
* RGB camera: `observation.images.ego`. Task string is required for training/inference.
* Executable modes initially: official 0 IDLE, 1 SLOW_WALK, 4 SQUAT, 5 KNEEL_TWO_LEGS.
  All 27 mode names exist in the schema; others fail closed until their transition/timeout
  behavior is commissioned. This does NOT mean every official mode is validated.
* Initial limits: planar speed ≤0.3 m/s, yaw ≤0.3 rad/s, upper reference slew ≤0.5 rad/s.
  Static modes require zero velocity. Explicit height overrides are conservatively restricted
  to 0.2–0.4 m in modes 4/5; actual planner behavior still requires sim verification.
* Mode transitions require IDLE in between and a one-second minimum dwell. These are command
  rules, not evidence that a physical transition has completed. Operators must wait for settling.

The wire codec is byte-tested against the pinned official Python builder (1280-byte header,
planner v1). Upper targets enter the C++ reference path; they never overwrite SONIC motor output.

## PICO collection boundary

Run PICO on a DIFFERENT publisher port (e.g. 5558), never competing with the gateway on 5556.
`sonic-pico --source tcp://<pico-host>:5558` accepts official `planner` messages containing
`upper_body_position[17]`, explicit speed and facing. It strips all hand fields and converts heading
changes to yaw rate. The gateway performs validation/slew before telemetry is recorded.

**Stock full-body PICO v3 is NOT a 29-joint stream.** At our pin its `joint_pos` is zero except
for wrists; SMPL carries the other body motion. Stock frozen-upper planner mode is supported as
a held reference, but it does not continuously track arms/waist. Continuous full-body PICO-to-joint
retargeting is an explicit integration gap, not silently replaced with measured angles or zeros.
For that path `sonic-pico --retarget your_module:convert` accepts pose bytes and requires a calibrated
converter returning `(Action, heading_radians)`. The converter must supply actual arm/waist
references and separately sourced mode/velocity/height. No such converter is bundled yet.

Recorder (on the camera/telemetry receiving host):

```bash
sonic-record --output data/episode000 --camera sonic_lerobot.camera:OpenCVCamera \
  --task 'kneel and reach forward' --seconds 30
sonic-export --episodes data/episode000 --root data/lerobot --repo-id local/g1
```

Choose success/failure/discard at episode end. Failed/incomplete/unclassified episodes are preserved;
discarded or incomplete episodes cannot be exported. Raw NPZ + JSONL retain timing, requested and
actually sent references. Recording uses the applied action, never measured angles as teacher action.
Recorder currently buffers an episode in memory; keep episodes short. Do not use it for hours-long capture.
Timing validation rejects large gaps; export resamples nearest frames to a uniform fps.
See [validation](docs/validation.md) for the limits of receive-time image alignment.

## π0 / π0.5

48 actions / 81 states exceed default 32-dimensional projections. Prepare enlarged pretrained
projections BEFORE fine-tuning; do not simply override config and load incompatible weights:

```bash
sonic-prepare-policy --base lerobot/pi0_base --output checkpoints/pi0-expanded \
  --dataset-root data/lerobot --dataset-repo-id local/g1
# For pi05, change both base/output above and policy.type below to pi05.
lerobot-train --policy.type=pi0 --policy.pretrained_path=checkpoints/pi0-expanded \
  --policy.max_action_dim=64 --policy.max_state_dim=96 \
  --dataset.repo_id=local/g1 --dataset.root=data/lerobot \
  --output_dir=checkpoints/trained --policy.push_to_hub=false
```

Preparation saves fresh pre/postprocessors with THIS dataset's statistics and absolute actions.
Use that same dataset during training; prepare again for a different dataset. `sonic-prepare-policy` copies
existing weights into expanded layers and zero-initializes added rows/columns. The enlarged model
MUST be trained; base policies do not understand these modes. One-hot mode channels use continuous
flow-matching loss in this initial design; argmax with ambiguity rejection is not a classification head.
Copy `sonic_schema.json` from the dataset into the final trained `pretrained_model` checkpoint directory;
retain the trained pre/postprocessor files. Merely copying the schema does not make a foreign policy compatible.

```bash
sonic-run --checkpoint <trained-pretrained_model-dir> --camera sonic_lerobot.camera:OpenCVCamera \
  --task 'kneel and reach forward' --fps 30
```

Models load and warm up before explicit arming. Inference runs in a worker while the main thread
consumes time-indexed chunks. Late frames are skipped, expired chunks cause HOLD, and reconnect
requires explicit re-arm/restart rather than replaying buffered actions. Inference must meet the
configured 0.4s latency ceiling; slower GPUs require measured timing and deliberate budget changes.
The ceiling also limits the observation age of every transmitted action, including while the next
inference is pending. Refresh begins no later than half that budget; sustained inference must fit
the remaining budget or execution enters HOLD. This deliberately limits long open-loop chunks.
Only the inference decoder snaps height within 0.02 of -1 to the default sentinel and static-mode
velocity components within 0.01 to zero. Larger deviations still face strict gateway validation.

## Loss handling

Gateway continues publishing at 50 Hz after GPU/PICO action loss (0.5s): keep the last applied upper
reference, zero movement, change slow walk to IDLE, preserve static squat/kneel mode and height.
State loss (0.25s) also disarms. Observation tickets expire and old epochs cannot resume control.
SONIC's own sensors must remain valid; state telemetry failure and loss of physical sensing are not equivalent.

Gateway process/deployment-host failure is NOT covered by a Python watchdog. Unmodified upstream
C++ resets to IDLE and clears upper references after a planner timeout. See
`patches/gear-sonic-timeout-hold.patch` for a pinned, opt-in C++ timeout change. It is source-checkable
but has NOT been compiled/run on hardware here. Without commissioning this path, do not claim
pose-preserving failure handling for gateway crashes. Neither implementation guarantees no falls.
